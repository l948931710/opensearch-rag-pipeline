# 阿里云工单：OpenSearch 向量检索版（HA3）文档写入成功后可检索索引静默丢失

> 提交前请补：实例 ID / 地域 / 联系人。以下正文可直接粘贴进工单。

---

**产品**：OpenSearch 向量检索版（Havenask / HA3 引擎）
**实例**：ha-cn-kgl4slr1n01（公网 endpoint：ha-cn-kgl4slr1n01.public.ha.aliyuncs.com）
**表**：fuling_kb_chunks（约 27,457 行，向量 dim=1024）
**严重程度**：高 —— 生产语料约 37%（485 篇文档 / 10,366 个分片）检索失明约 5 天，
线上问答已受影响。

## 一、现象

2026-07-06 16:30–17:40 与 2026-07-07 10:30–11:00 两个时间窗内，我方通过 SDK 实时
写入（cmd=add，按主键 id 整行 upsert，批大小 8–100，合计约 10,366 行）。**写入 API
全部返回成功**，写入后立即执行的自查询校验也通过。但这些行随后出现如下不一致：

1. **按主键 filter 点查可取回完整字段**（`filter="id=<pk>"`，正文与属性都在）——
   doc store 层数据完好；
2. **同一行在向量检索与文本检索中均无法召回**：
   - 用该行自身存储正文做查询向量、kNN 混合检索——**不返回该行**（抽样 15/15 复现）；
   - 用该行正文中的唯一业务编号做 BM25 文本检索——返回多个含同类编号的其它文档行，
     **唯独不含该行本身**；
3. 零向量 range-scan 枚举（`filter="id>=lo AND id<hi"`）能列出这些 id；引擎 docCount
   与我方 RDS 侧行数一致。

即：**doc store / 属性层可达，但倒排索引与向量索引不包含这批行**。期间未执行任何删除。

## 二、关键定位证据（请重点关注）

1. **延迟性**：写入当时的自查询校验通过（写入成功且短时可召回），是**数小时后**才
   静默变为不可召回——不是写入失败，是索引在写入成功之后丢失。这与本实例
   2026-07-06 上午的一次同类事件吻合：当时 09:32 全表对账缺失=0，11:30 变为
   缺失=69（时间窗内无任何删除操作），其中 6 行是当天 09:15 写入并验证过的。

2. **重新写入可恢复（已实测）**：我方对其中 1 篇文档（1 个分片）执行完全相同的
   重新 upsert（同一 id、同一向量、同一正文），**该行立即恢复可被自查询召回（rank 1）**。
   说明：原始数据无损坏、id/向量/正文均正确——**丢失发生在索引侧**，重新触发一次
   索引即可修复。这把根因范围收敛到：**实时段（realtime segment）的索引构建 / 段合并
   环节丢弃了这批已写入的文档**。

3. **共同诱因**：两个丢失窗口都是**短时间大批量实时写入**（约 40 分钟内约 1 万行）。

## 三、我方已排除

- 写入失败 —— API 全部成功，点查字段完好，重写即恢复；
- 数据损坏 / 向量维度错误 —— 点查取回的向量维度、正文均正确；
- 权限 / 过滤条件 —— 受影响行 permission_level=public，健康行与故障行过滤条件一致；
- 手动删除 —— 时间窗内无任何删除 API 调用；
- 客户端检索逻辑 —— 同一套检索代码对 6 月写入代次的行工作正常（见对照样本）。

## 四、请求协助

1. 排查该表 **2026-07-06 16:00 起** 的实时段构建 / 段合并（segment merge / build）日志与
   段状态，确认这批行是否停留在未建索引的实时段、或在段合并过程中被丢弃；
2. 给出根因与修复建议；我方可重新写入全部受影响行，但**需要确认重写后不会再次丢失**
   （或提供避免复发的写入参数：写入速率 / 批大小 / 段合并配置上限）；
3. 若为已知问题，请提供规避方案与是否需要工单侧执行的补救（如强制段合并 / 索引重建）。
